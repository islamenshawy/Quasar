# Architecture Decision Log

Every decision that is expensive to reverse gets an entry here. Decisions are never deleted: when one changes, the old entry is marked **Superseded** and a new entry explains why.

Status values: **Accepted**, **Proposed** (waiting for input), **Superseded by ADR-xxx**.

| ID | Date | Status | Decision | Rationale / consequences |
|---|---|---|---|---|
| ADR-001 | 2026-09-28 | Accepted | Java 21, Spring Boot 3, jPOS, PostgreSQL | jPOS has BASE24 channel/packager support; `BigDecimal`/integer money; mature SOAP tooling (Dexxis); payments hiring pool is Java-heavy. Node.js was evaluated and rejected for the core. |
| ADR-002 | 2026-09-28 | Accepted | PIN method: Visa PVV + PVKI | Matches existing practice. PIN never stored, never in clear in software; only the HSM sees it. |
| ADR-003 | 2026-09-28 | Accepted | Money stored as BIGINT minor units | No floating point anywhere in the ledger. |
| ADR-004 | 2026-09-28 | Accepted | PAN at rest: AES-256-GCM + HMAC-SHA256 lookup hash | PCI DSS req. 3. Test keys from env; production needs a KMS (CMS-061). |
| ADR-005 | 2026-09-28 | Accepted | CVV1/iCVV/CVV2 generated by HSM on demand, never stored | PCI DSS 3.3. Deterministic, so re-derivable. |
| ADR-006 | 2026-09-28 | Superseded by ADR-010 | Dexxis calls CreateCard, idempotent on request id | Replaced by operator-driven issuance. |
| ADR-007 | 2026-09-28 | Accepted | Card lifecycle: PENDING_PRINT → ACTIVE only after print + PIN set | A failed print can never produce a usable card. |
| ADR-008 | 2026-09-28 | Proposed | ISO dialect: BASE24 ISO 8583:1993 per client spec | Waiting for the spec and traces (CMS-051). |
| ADR-009 | 2026-09-28 | Accepted | Real payShield 10K (test LMK) is the reference for L6 testing | Simulator results must be confirmed on real hardware before external connections. |
| ADR-010 | 2026-09-28 | Accepted | Operator issues card in CMS; Dexxis searches by PAN for perso data | CMS is the system of record for customer, account and card. |
| ADR-011 | 2026-09-28 | Accepted | Product eligibility matrix: account type × customer segment × currency | Supports multiple card types and segments; enforced in service and screen. |
| ADR-012 | 2026-09-28 | Accepted | Perso data only while PENDING_PRINT; every fetch counted and audited | Printed or active cards cannot be re-personalised via Dexxis. |
| ADR-013 | 2026-09-28 | Accepted | Account type carries `ledger_mode` (CMS_LEDGER / CORE_BANKING) | The auth engine decides where funds are checked per account type. |
| ADR-014 | 2026-09-28 | Accepted | hsm-sim: protocol-level payShield simulator, real algorithms, fixed test keys | Development without HSM access, with no separate code path in the CMS. Same clear keys give the same PVV/CVV as the real HSM. Cryptograms are not portable; keys are re-imported on the real HSM. |
| ADR-015 | 2026-09-28 | Accepted | HSM connections opened lazily; HSM state exposed via health endpoint | CMS must start and alert when the HSM is down, not crash. |
| ADR-016 | 2026-09-28 | Accepted | SemVer + Keep a Changelog + Flyway forward-only migrations + git tags | Every environment can report exactly what it runs (`/api/version`), and every change is traceable to a version and a roadmap item. |
