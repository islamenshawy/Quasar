Status values: **Accepted**, **Proposed** (waiting for input), **Superseded by ADR-xxx**.

| ADR-018 | 2026-09-30 | Accepted | Reference data is configuration in the database, maintained from the console and audited; rows are deactivated, never deleted | Segments, account types, currencies, products and eligibility change without a release or SQL. | ADR-020 | 2026-10-01 | Accepted | Authorization engine: one DB transaction per request, card and account rows locked; retransmissions answered from the stored response; ATM withdrawals and purchases single-message (post at once), pre-authorisations hold funds until completion, reversal or expiry | Serialises activity per card/account without distributed locks. Idempotent under switch retries. Matches BASE24 ATM (1200/1420) and POS dual-message (1100/1220) flows. |
| ADR-021 | 2026-10-01 | Accepted | Stand-in advices are booked without checks (balance may go negative); advices in a currency other than the account's are acknowledged but not booked and flagged for review | The switch already approved the cardholder; refusing an advice would only desynchronise the ledger. No FX in the CMS. |
| ADR-022 | 2026-10-01 | Accepted | BASE24 interface: own TCP server with jPOS GenericPackager; field layout in an XML file, framing (length prefix, header) in configuration; built provisionally before the spec | Lets the engine be exercised end to end now. Aligning with the real spec (IN-01) is a data change in `iso/base24-1993.xml` and `cms.iso.*`, plus mapping review in `IsoMapper`. |
| ADR-023 | 2026-10-01 | Accepted | Console sign-in with local users (BCrypt), server session cookie + CSRF token; HTTP Basic for scripts; Dexxis by API key; four roles | Works without external identity infrastructure in TEST; the user store sits behind Spring Security, so LDAP/SSO (CMS-067) replaces it without touching the API. |
| ADR-024 | 2026-10-01 | Accepted | Maker-checker as a generic, policy-driven approval queue; submission runs the action in a rolled-back transaction to validate it; the checker must differ from the maker; the action executes as the maker | Four-eyes control for configuration and money movements, configurable per action by an administrator. Makers see validation errors immediately; checkers never approve something that was invalid when submitted. |
| ADR-025 | 2026-10-01 | Accepted | A PAN may have several cards (PSN 00, 01, ...); renewal / damaged replacement keeps the PAN, compromised cards always get a new PAN; the replaced card stops at activation of the new one | Customers keep their number (standing orders, wallets) across renewals, with no gap in service; compromised numbers never come back. Lookups by PAN must pick the right card (production card for Dexxis, expiry match for authorization). |
| ADR-026 | 2026-10-01 | Accepted | Batch jobs in the CMS: cron per job in the database, a row claim per run so a job never overlaps itself, per-item transactions, history kept | No external scheduler needed in TEST; operations can see and re-run jobs from the console. Multi-instance HA is covered by the claim; a dedicated scheduler can replace the trigger later (CMS-064). |
| ADR-032 | 2026-10-03 | Proposed | Issuer scripts are queued in the CMS and delivered only on an online chip transaction whose ARQC verified, MAC'd by the HSM per transaction (session key from the ARQC); results come back in 9F5B. The card verification value checked follows the entry mode: iCVV for chip reads, CVV1 for magstripe, CVV2 for card-not-present | Scripts cannot be replayed (the MAC binds them to one ATC / ARQC) and never block a payment; checking the value that matches the read makes chip data useless on a cloned stripe. Proposed until IN-03 confirms the KU layout and key ownership. |
| ADR-031 | 2026-10-03 | Accepted | Notifications use a transactional outbox in the CMS database and an asynchronous dispatcher; one-time passwords are stored as salted hashes and redacted from the outbox once sent | No message for a rolled-back transaction, no lost message when the gateway is down, no authorisation waiting for SMS delivery; OTP codes never sit in clear text at rest after delivery. |
| ADR-030 | 2026-10-03 | Accepted | Fees live in plans referenced by products; one rule per event and region, fixed + percent with min / max and monthly free uses; event and periodic fees are idempotent per card, event and period. Foreign currency is converted to the account currency at authorisation with a maintained rate table, the markup posted as its own journal | Pricing changes without touching products or code, under maker-checker; charging twice is impossible by construction; limits, funds and statements stay in one currency per account. |
| ADR-029 | 2026-10-03 | Accepted | Fraud screening runs inside the authorisation (synchronous, same transaction) with declarative rules stored as JSON conditions; a score threshold complements per-rule actions; alerts are a queue with explicit outcomes | Declines happen before money moves and alerts commit with the decision. Rules change without a release, under maker-checker. A scoring model or external engine can later feed the same verdict. |
| ADR-028 | 2026-10-03 | Proposed | Core banking accounts are authorised online against core; the CMS keeps no balance for them. Proposed until IN-06 confirms core's API, idempotency and the bank's stand-in policy. |
| ADR-027 | 2026-10-01 | Proposed | EMV: the CMS verifies ARQC and returns ARPC (method 1) through the HSM with the issuer IMK-AC; the host builds the data block from field 55 using a per-product tag list; ATC must increase per card | Keeps all chip crypto in the HSM and makes the CDOL-dependent part configuration. | ADR-019 | 2026-09-30 | Accepted | Numbering: CIF source is a setting (CMS_GENERATED / CORE_BANKING / EITHER); each account type is CMS_GENERATED from a `number_sequence` or CORE_BANKING | Supports CMS-held products (prepaid) and core-banking products (current/savings) side by side. Sequences lock their row and skip numbers already typed in manually. |
